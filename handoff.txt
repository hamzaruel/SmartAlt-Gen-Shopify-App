LARGE-STORE RELIABILITY — PER-IMAGE RETRY QUEUE  (Phase 1 ✅  Phase 2 ✅ verified)
================================================================================
WHY: the old generation flow held the whole image list in memory / one JSON blob
and SILENTLY DROPPED images that failed AI generation (job still reported "done").
Fatal at 100k–200k+ stores and dishonest for an accessibility product. Rebuilt as
a per-image retry queue so NO image is ever skipped without being accounted for.

CORE MODEL (lib/generationJob.js)
  - ONE ROW PER IMAGE in `generation_queue`, keyed (shop, kind, image_key);
    status: pending -> processing -> done | failed; tracks attempts, next_attempt_at,
    alt, last_error. Control row per (shop, kind) in `generation_jobs`.
  - kind = 'manual' (Generate page) | 'bulk' (Bulk edit + scheduler). One shared
    engine; the two kinds run on independent queues and never collide.
  - Invariant: a job is "complete" only when EVERY image is terminal (done or
    permanently failed). Replaces the old generation_results table + queue blob.

FAILURE / RETRY (the four review-hardened fixes — all verified)
  1. Image faults (dead URL, decode, content block): consume an attempt, retry
     with backoff (5s, 30s), permanently `failed` after MAX_ATTEMPTS=3. Surfaced
     to the merchant with a "Retry failed" button (/api/generate/retry).
  2. Service faults (Gemini 429/503/overloaded): do NOT burn an attempt — pause
     the job (paused_service, escalating 5/15/30 min) and auto-resume.
  3. Plan-quota exhaustion (our meter): surfaced pause (paused_quota), auto-resumes
     at the next billing cycle (resume_at = currentPeriodEnd; Free/none = upgrade).
     NB: plan-quota (next cycle) is split from Gemini-quota (short retry).
  4. Crash safety: the CLAIM (pending->processing, guarded by rowsAffected===1) is
     the concurrency gate; done + usage increment commit in ONE db.batch (no double
     bill); stranded `processing` rows reclaimed only when older than 4 min.

AUTO-RESUME: scheduler tick (lib/scheduler.js) runs sweepResumableJobs() every 60s
  — resumes any paused job (manual via runJob, bulk re-enters its orchestrator),
  refreshing entitlement on quota resume. Tab-independent. + hourly TTL cleanup.

BULK (Phase 2 — lib/bulkRun.js, now fully streaming; no getAllImages/toApply walls)
  - Phase machine, re-entrant by `phase`: scanning (packet-by-packet seed) ->
    generating (AI via shared engine; title/template/remove computed in DB pages)
    -> applying (write-back in pages of 25, drop applied rows) -> finished.
  - getBulkRun() reads the unified generation_jobs(kind='bulk') row; bulk/status +
    client poller handle paused/failed states. bulk_runs table is retired.

GDPR: deleteGenerationData(shop) wired into app/uninstalled + shop/redact.

VERIFICATION: app/api/verify-queue (HARD-GATED: 404 unless ALTGEN_TEST_HOOK=1;
  also makes generateWithGemini deterministic + shrinks timers). 9/9 pass against
  the live Turso DB — covers happy path, permanent-fail, flaky retry, service
  pause, crash recovery, retry-failed, quota cap, auto-resume sweep, and manual+
  bulk coexistence. STAGING-PENDING: bulk's scan (scanPacket) + write-back
  (embedAlts) need a real shop token — run one small bulk edit on staging to
  confirm scan->generate->apply end-to-end.

NEXT (Phase 3, not started): Gemini Batch Mode for the 200k INITIAL backfill (the
  cost/throughput win; this queue is the real-time/correctness layer). `batch_id`
  column already reserved on generation_queue so no further migration is needed.

WHAT THIS APP IS
----------------
Embedded Shopify app (Next.js 14, App Router + Pages Router). Scans a store's
images (products, files, articles, collections), classifies alt-text quality,
generates WCAG-compliant alt text (Gemini AI or rule-based title templates), and
writes it back to Shopify. Identity = the shop domain. DB = Turso (libsql).
Auth = OAuth + App Bridge session-token exchange. Display name "Alt Text Pro";
toml/registered name + handle are still "SmartAltGen"/"smartaltgen-2".

12. BULK EDIT + SCHEDULING (Hextom-style "Start now / Schedule later", auto-apply)
   - Auto-write-back: a bulk run GENERATES alt text AND writes it to Shopify in one
     pass (no separate Embed step). Runs server-side in the PM2 process.
   - lib/bulkRun.js: runBulkEdit(shop, config) → offline token → getAllImages →
     filter (sources / scope missing|all / skipExisting) → generate (AI via Gemini,
     or template/title server-side) → embedAlts → meter usage + settle overflow.
     Progress in its own Turso table `bulk_runs` (one row/shop), polled by the tab.
   - Immediate: POST /api/bulk/start (fire-and-forget) → poll /api/bulk/status.
   - Scheduling: lib/scheduledTasks.js + Turso `scheduled_tasks`. Recurrence
     once|daily|weekly. The FIRST next_run_at is computed CLIENT-side (knows the
     merchant tz) and stored as an absolute epoch; the server only ADDS 1d/1w for
     recurring runs (no server tz math). API: /api/schedule (GET list, POST create,
     DELETE remove). "Run now" just calls /api/bulk/start with the task's config.
   - Scheduler: instrumentation.js register() → lib/scheduler.js startScheduler().
     60s tick: getDueTasks (next_run_at<=now) → markRunning (atomic claim) →
     runBulkEdit → finishRun (re-arm daily/weekly, or finish 'once'). Self-heals on
     restart (state in Turso). Requires experimental.instrumentationHook=true in
     next.config.js (added).
   - UI: Alt-text-studio page gained a "Bulk edit & schedule" block (scope radios,
     Start Bulk Editing, Schedule Bulk Editing with Once/Daily/Weekly + time) reusing
     the existing type/mode/skip/AI-info/instructions controls, plus a "Scheduled
     bulk edits" manager (list, run-now, delete). Bulk operates on the SELECTED type.
   - TOKEN FIX (required for autonomous runs): shops table now has an `offline_token`
     column (long-lived, captured at OAuth install, NEVER overwritten by the online-
     token refresh in serverAuth). bulkRun/scheduler use getOfflineToken(shop).
     ⚠️ Shops that installed BEFORE this change have no offline_token → getOfflineToken
     falls back to the (short-lived) access_token, which works for immediate runs but
     a scheduled run days later may hit an expired token. Fix: reinstall, or backfill.
   - GDPR: app/uninstalled + shop/redact now also deleteTasksForShop(shop).
